## UI-REVIEW-002：商品启用/停用语义需要闭环

- 状态：确认需要修改，待全部页面交付完成后统一实施。
- 权限决策：商品停用必须使用独立权限，至少与商品新建、编辑权限分离；前端按权限显示操作入口，后端必须独立鉴权，不能仅依靠前端隐藏按钮。
- 设计语义：`enabled=false` 应保留商品及历史记录，但禁止该商品进入新的入库、销售、预留和出库流程。
- 当前实现观察：后端已保存并支持按 `enabled` 查询商品，前端也支持显示、筛选和编辑该状态；但尚未发现入库、销售和库存分配 Service 对停用商品进行统一拦截。
- 风险：界面显示“停用”可能让用户误以为业务已经被完全禁止，而后端实际上仍可能接受该商品的新业务单据。
- 后续决策：统一设计停用申请与确认流程、停用原因和审计记录、重新启用权限、既有库存处置规则、在途单据规则，以及应在哪个统一服务层实施校验。

## UI-REVIEW-003：销售订单 Excel 模板改为可维护的静态模板

- 状态：确认需要修改，待全部前端页面交付完成后统一实施。
- 当前实现：后端使用 Apache POI 在每次下载时从零生成工作簿，模板样式需要修改 Java 代码，且现有中文表头存在历史编码乱码。
- 目标方案：采用“外部静态模板优先、项目内置默认模板兜底、客户与商品基础数据下载时动态写入”的混合模式。
- 用户维护方式：运营人员可直接使用 Excel 修改外部模板的配色、字体、Logo、列宽和填写说明，不需要修改 Java 代码。
- 安全约束：后端返回模板前校验工作表、表头、列顺序和数据起始行；外部模板缺失或损坏时自动回退到内置模板。
- 后续决策：全部页面完成后统一确定模板视觉规范、动态下拉数据范围、模板版本号和部署环境下的外部模板目录。

## UI-REVIEW-009：渠道集成业务链路与信息架构整体重梳理

- 状态：确认需要整体重新评审，当前保留已交付功能，待全部页面完成后逐步梳理和修改。
- 评审范围：店铺配置、待处理 SKU、SKU 映射管理、人工复核四个入口的名称、职责边界、使用顺序、角色权限、页面信息层级和跨页面跳转关系。
- 核心问题：当前页面按后端技术对象划分，业务人员不容易理解“现在发生了什么、为什么需要处理、处理后订单去哪里”，正常同步链路与异常处理链路也需要更清楚地区分。
- 梳理方法：先基于真实运营场景确定角色与任务，再绘制订单同步、商品识别、人工放行和失败恢复流程，最后确定页面结构、状态文案、操作权限及所需后端接口，不直接从现有菜单名称反推业务。

- 验收目标：非技术运营人员进入渠道模块后，能够立即识别店铺、看到待办、理解处理后果，并能沿一条明确路径完成一次异常订单恢复。

## UI-REVIEW-010：工作台布局与经营分析体系重构

- 状态：确认需要重新设计，当前保留已交付的待办聚合能力，待全量前端验收后进入第二轮优化。
- 用户反馈：现有工作台布局较混乱，无法直观看到利润、销售表现等核心经营数据，页面的信息优先级与管理视角不足。
- 推荐结构：采用“双层首页”。“工作台”面向日常执行，集中展示待审批、待映射、异常事件、缺货和快捷操作；另建“经营分析/管理驾驶舱”，承载销售额、毛利润、毛利率、订单量、客单价、趋势及商品/客户/渠道贡献分析。
- 首页边界：工作台顶部可保留少量摘要指标和“进入经营分析”入口，但不堆叠完整图表；仓库、销售、采购和管理角色应看到各自优先级不同的首页内容。
- 数据前提：利润不能直接用销售额减商品主数据价格粗算，需要先确定销售收入、销售成本、退货、折扣、税费、运费、汇率和时间口径，并确认采用移动平均、批次实际成本或其他成本法。
- 实施顺序：先确认经营指标口径和角色需求，再设计汇总 API/汇总表，最后制作页面原型并开发，避免先画图表后补数据定义。
- 验收目标：用户进入系统后能够在十秒内回答“今天有什么必须处理、销售表现如何、利润是否异常、问题集中在哪里”。

## ARCH-REVIEW-011：多仓 SKU 经营策略下沉

- 状态：已确认加入待完成工作，当前仅登记方案，不修改数据库、接口或现有业务逻辑；计划纳入多仓能力建设阶段。
- 当前基线：`ProductSku` 目前以全局字段保存 `minStock`、`safetyStock` 和 `leadTime`。同一 SKU 在不同仓库只能共用一套阈值，无法表达广州仓安全库存 100、深圳仓安全库存 20 这类真实经营差异。
- 目标模型：新增“公司 + SKU + 仓库”唯一的经营策略关系，建议暂命名为 `sku_warehouse_policy`；商品主数据继续回答“它是什么”，关联策略回答“该商品在这个仓库如何经营”，库存批次与预留账本继续回答“现在有多少、已占用多少”。
- 策略范围：最低库存、安全库存、补货点、采购提前期、默认库区或默认上架范围、是否允许在该仓销售、是否允许采购进入该仓，以及结构化的仓库级补货/分配策略。不得使用无法校验的自由 JSON 代替明确字段和枚举。
- 口径前置：实施前必须先消除当前 `minStock` 与 `safetyStock` 语义重叠。建议将安全库存定义为需求波动缓冲量，将补货点定义为“提前期预计需求 + 安全库存”；“最低库存”若没有独立业务含义，应作为兼容字段迁移后废弃，不能保留三个含义近似的阈值。
- 业务接入：库存预警与补货建议按仓库独立计算；销售/ATP/预留必须遵守该仓销售开关；采购建单和收货目标仓必须遵守采购开关；默认库区只用于上架推荐，不能绕过库位防混放、批次隔离和容量校验。
- 数据迁移：根据现有 SKU 全局阈值，为当前已经营该 SKU 的仓库生成初始策略记录；迁移期间保留全局字段作为只读默认值，完成服务切换和数据核对后再废弃，禁止一次性删除导致旧流程失效。
- 前端范围：在 SKU 详情中增加“仓库策略”区域，以紧凑表格维护各仓阈值、经营开关和默认库区；不把这些仓库差异属性继续堆入商品基础信息表单。
- 架构约束：不得改变 `Available = OnHand - Reserved`、批次库存真相源、FEFO 和现有预占账本；仓库策略只决定可经营范围、预警和分配规则，不直接保存或修改库存数量。
- 验收场景：同一 SKU 在两个仓库可设置不同阈值并分别触发预警；关闭某仓销售或采购后只影响该仓；策略关系在同一公司内不得重复；历史订单和库存流水不因策略修改而被回写；无仓库策略时必须采用明确且可审计的默认行为。
