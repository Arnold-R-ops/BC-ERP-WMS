## 1. 本阶段交付结果

P0-03A 已在库存批次上建立独立于物理生命周期的质量状态真相，并把可售判定统一下推到库存查询、销售预留、自动分配、缺货回补和出库扣减。库存仍按实际在库数量统计；只有质量状态为 `AVAILABLE`、批次有效且未到期的库存可以参与销售履约。

本阶段支持以下七种权威质量状态：

- `AVAILABLE`：质量状态允许销售；仍须通过启用状态、库位和有效期门禁。
- `PENDING_INSPECTION`：待检。
- `QUARANTINED`：隔离。
- `DAMAGED`：破损。
- `EXPIRED`：过期。
- `RECALL_HOLD`：召回冻结。
- `RETURN_INSPECTION`：退货待检。

`InventoryBatch.active` 继续只表示物理库存行是否有效，不再承担质量或可售含义。

## 2. 可售门禁

- `InventoryBatch.isSaleable()` 成为批次级统一判断：库存行有效、质量状态为 `AVAILABLE`、且有效期未过。
- 可用库存汇总只计算通过门禁后的 `quantity - reservedQuantity`；在库数量仍包含全部有效物理库存。
- FEFO 候选查询只返回可售、有库位、有剩余可用量且未过期的批次。
- 自动分配、指定批次分配、缺货回补和销售录单批次选项均使用同一可售候选集。
- 出库在直接扣减和消耗预留两个入口再次校验可售状态，避免绕过上游分配门禁。
- 不可售库存不会抑制低库存提示或补货预测。
- 既有按有效期阻止过期商品销售的安全规则继续保留；P0-03A 不引入自动改写 `EXPIRED` 的定时任务。

## 3. 状态变更基础设施

- 新增仅供后续受控业务流程调用的 `InventoryQualityStateService`，没有提供通用前端按钮或公共 Controller。
- 状态变更锁定库存批次，并在同一事务中完成状态更新、不可变事件和 Outbox 事件。
- 每个状态变更要求幂等键；相同请求安全重放，不重复产生状态事件。
- 事件保存原状态、目标状态、数量快照、来源业务、原因、服务端操作人和请求指纹。
- 禁止空操作、无效库存行和把已过期批次恢复为 `AVAILABLE`。
- `AVAILABLE` 批次仍有销售预留时，不允许直接转为不可售状态；必须先由后续业务流程释放或重新分配预留，避免产生悬空销售承诺。
- 状态服务只提供一致的事务边界；质检、冻结、召回、退货和处置流程仍须在各自阶段实施权限与状态机规则。

## 4. 数据库迁移

新增迁移 `V4_78__Inventory_Quality_Status_Truth.sql`：

- 为 `inventory_batch` 增加非空 `quality_status`，已有活动和历史批次统一回填为 `AVAILABLE`。
- 回填不重放库存、不新增库存流水，也不伪造历史状态事件。
- 增加质量状态合法值约束，以及“不可售状态不得保留销售预留”的数据库约束。
- 新增租户隔离的 `inventory_status_event` 追加式事件表，使用复合租户外键、租户内幂等唯一键、强制 RLS 和禁止更新/删除的数据库触发器。
- 租户清除流程仍可在明确的 `app.tenant_purge=on` 上下文中删除事件，避免阻断合法的数据生命周期操作。

本次已通过迁移静态契约测试、Hibernate PostgreSQL 实体建表及全量集成测试验证新模型。由于现有开发库的 V4.73 已应用校验和与当前代码不同，未对该库执行 Flyway `repair`，也未把 V4.78 试探性应用到开发数据。上线前仍应在隔离的真实数据副本中完成 V4.73 校验和处置决策及 V4.78 Flyway 彩排。
