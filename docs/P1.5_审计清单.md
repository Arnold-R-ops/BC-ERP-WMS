# P1.5 数据模型正名审计清单

## 1. 审计结论

当前系统中名为 `Product` / `products` 的对象实际承担 SKU（库存、采购、销售和履约最小单元）职责；名为 `ProductSpu` / `product_spu` 的对象实际承担产品（SPU）职责。本次统一为：

- `Category` / `categories`：产品类别树。
- `Product` / `products`：产品（SPU），归属一个二级类别。
- `ProductSku` / `product_skus`：具体规格（SKU），归属一个产品，是所有库存与交易引用的主体。

真实数据库只读审计日期：2026-07-16。Flyway 当前已执行至 V4.17；V4.18、V4.19、V4.20 必须在同一发布窗口按序执行。

## 3. Java 引用

必须同步正名的区域：

- 实体关联：`InventoryBatch`、`Inventory`、`InboundOrderItem`、`PurchaseOrderItem`、`SalesOrderItem`、`StockTransaction`、`StocktakeItem`、`ChannelSkuMapping`。
- 仅保存 ID 的账本：`InventoryReservation`、`BackorderLine`、`EmergencyStockCorrection`、`OutboundTask` 及其 DTO。
- Repository 派生查询、JPQL、原生 SQL：库存汇总、FEFO 分配、ATP、补货预测、盘点、渠道 SKU 映射。
- Service/Controller/DTO：所有原 `productId`（SKU 语义）改为 `productSkuId`。
- API：SKU 主数据改为 `/api/product-skus`；`/api/products` 专用于 SPU 产品。
- 前端：商品运营台、采购、入库、销售、库存、渠道映射全部切换至 `productSkuId`。

## 4. 类别迁移规则

旧 `product_spu.category` 是产品级分类的唯一权威来源。迁移采用确定性规则：

1. 每个非空旧分类建立一个一级 Category。
2. 在该一级分类下建立固定二级节点“未细分”，产品绑定此二级节点。
3. 旧分类为空、空白或无法识别时，产品绑定 `未分类 / 待整理`。
4. 旧 SKU 表上的文本 `category` 不再作为分类事实来源，迁移后删除，避免同一产品下 SKU 分类互相冲突。

## 5. skuCode 规则

- 历史 SKU：`SKU` + 8 位旧 SKU ID，例如 ID 12 为 `SKU00000012`。
- 新 SKU：从数据库独立序列取号，格式同上；与条码无关、创建后不可修改、删除后不复用。
- `barcode` 仍是当前唯一主条码；一 SKU 多包装条码留待后续独立模型扩展。
- 新内部批次码使用规范化产品标识、不可变 `skuCode` 和日期生成；条码不参与批次身份，长编码会按固定预算安全截断。

## 6. Outbox 与兼容边界

- 已发布的历史 Outbox payload 不改写；旧 `productId`、`aggregateType=Product` 保留当时的 SKU 语义。
- 新事件使用 `schemaVersion=2`、`productSkuId`、`aggregateType=ProductSku`。
- `V4_20` 只转换尚未发布的旧事件为 V2 契约，避免新消费者误读；已发布历史保持不可变。
- 本次不保留旧 `/api/products` SKU 接口兼容层，前后端必须同版本发布。

## 7. 发布门禁

1. `mvn test` 全绿（改名前基线为 1041/1041）。
2. V4.18-V4.20 在临时 PostgreSQL 副本完整执行。
3. 迁移前后核对 Product、ProductSku、批次、订单行和渠道映射行数。
4. 校验所有 `product_sku_id` 外键、唯一索引与序列。
5. 重新导出 OpenAPI，前端类型检查、单测和构建全绿。
6. 真实库备份完成且通过 `pg_restore --list` 可读性检查后，才允许发布。
