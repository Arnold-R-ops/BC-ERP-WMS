## 2. 实施结果

### 2.1 销售出库统一记账

- 单笔和批量发货不再直接改批次数量或自行插入库存流水。
- 发货使用稳定 `postingId=SALE-OUT:<taskId>` 和幂等键 `sale-out-task:<taskId>`，批次扣减、流水和 Outbox 在同一事务中完成。
- 有销售预留时先消费权威开放预留，再执行一次实存扣减，避免重复扣库存。
- 锁顺序收敛为销售单、批次、预留、任务；批量请求先按 ID 排序，降低并发死锁风险。
- 前端在失败重试时复用同一业务意图的 `Idempotency-Key`，成功、取消或切换任务后才换键。

### 2.2 盘点统一记账与精确重放

- 盘盈和盘亏都通过统一记账服务，来源、仓库、批次、操作者、posting 和幂等信息完整。
- 盘点审核要求 `Idempotency-Key`，任务和批次使用悲观锁；每条差异产生确定性的子 posting 标识。
- 业务结果与序列化响应在同一事务中写入幂等记录。相同键重放返回首次提交的精确响应，不读取后来已经变化的任务状态冒充历史响应。
- 盘点提交、结束和审核统一以任务行作为领先锁；未完成全部明细时不能结束或批准，避免已开始的盘点提交与审核并发交错。
- 每次复盘都重新计算差异统计；统一过账后刷新库位占用状态，盘亏至零和盘盈重新启用批次时不会留下库位状态漂移。
- 创建任务、审核和明细查询都执行仓库范围校验；月度选批改为数据库查询，不再加载整本库存账。

### 2.3 公共预留释放收口

- 删除 `POST /api/inventory/reservations/{id}/release` Controller、服务方法和 OpenAPI 暴露。
- 保留订单取消等内部 `releaseOpenReservationsForOrder` 业务能力；内部释放先锁销售单，再按批次和预留 ID 的确定顺序加锁，并以数据库中的开放数量为准。
- 剩余预留查询只要求 `inventory:view` 或 `TENANT_ADMIN`，不能借查询权限执行释放；仓库人员的结果按分配仓库过滤，内部鉴权使用的 `warehouseId` 不进入 JSON 或 OpenAPI。

### 2.4 OpenAPI、TypeScript 与前端

- 从当前运行 JAR 的 `/v3/api-docs` 重新导出 `docs/frontend/openapi.json`，再生成 `frontend/src/api/schema.d.ts`。
- 当前契约共 303 条路径；公共预留释放、采购直接收货、旧入库直接收货和旧直接调拨路径匹配数均为 0。
- 销售发货和盘点审核在 OpenAPI 中都明确声明必填 `Idempotency-Key`。
- 前端类型检查、生产构建和串行全量 Vitest 均通过；全量结果为 81 个文件、316 项测试。

### 3.2 V4.76 上线前门禁

V4.75 允许 `expiry_date < production_date`，V4.76 新模型拒绝这一历史事实。迁移不得猜测哪一个日期正确。维护窗口开始前必须对每个租户分别执行下列预检；`<tenant-id>` 必须替换为正在检查的真实租户 ID。应用角色受 FORCE RLS 约束，不能省略租户上下文，否则查询可能错误地返回 0 行：

```sql
BEGIN;
SELECT set_config('app.company_id', '<tenant-id>', true);

SELECT company_id, id, inbound_order_id, production_date, expiry_date
FROM inbound_order_items
WHERE company_id = current_setting('app.company_id')::BIGINT
  AND production_date IS NOT NULL
  AND expiry_date IS NOT NULL
  AND expiry_date < production_date
ORDER BY company_id, id;

ROLLBACK;
```

结果非空时停止升级，由业务人员形成可审计修正后再在克隆库重演。V4.73 连续升级还应在停写维护窗口执行，避免 V4.74/V4.75 中间态业务数据在迁移过程中产生。

### 3.3 checksum 边界

A1 为修复 FORCE RLS 下的历史回填，修改了已编号的 `V4.80` 和 `V4.82`，因此它们的 Flyway checksum 已改变：

- 全新生产空库，以及尚未执行 V4.80/V4.82 的历史起点，可以使用当前脚本正常升级。
- 本报告的 V4.83 是由当前脚本生成的**合成夹具**，不是已经登记旧 checksum 的真实 V4.83 备份，不能证明真实旧库可直接升级。
- 若任何需保留的数据库已经执行旧版 V4.80/V4.82，Flyway validate 会正确阻断。禁止关闭校验或静默 `repair`；必须先备份，在克隆库比对旧脚本与业务事实，并取得单独批准后决定重建或受控 checksum 处置。
- P0-04C 报告中“V4.79～V4.81 未修改”只是当次阶段证据，已被本次 A1 修复取代。

正式生产按用户确认采用全新数据库，因此不会继承开发库旧 checksum；现有开发/测试库也不得在未评估时直接套用当前迁移链。

## 6. 当前唯一业务口径

- 采购页面不直接收货。采购分仓并生效后，由快捷“确认发货”或复杂 ASN 管理生成统一收货任务，仓库在独立收货工作区落账。
- `/inbound` 是可开关的“其他入库申请”，不是采购收货或仓间调拨；确认后同样进入统一收货。
- 普通采购默认 `NONE`，短收关闭默认 `DIRECT_WITH_REASON`；审批是可选治理能力。
- 收货质检默认关闭、质检放行默认 `DIRECT`；启用时先形成实收库存并进入 `PENDING_INSPECTION`。
- 销售列表分别展示业务主状态、库存分配和仓库进度；旧混合状态不再是业务真相。
- RMA 必须关联原销售和出库证据；调拨只处理同一租户内不同仓库。
- 质检、库存处置和 RMA 当前没有照片/附件上传要求；图片存储方案以后单独确认。
