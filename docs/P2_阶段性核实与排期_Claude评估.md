## 三、三件当务之急（Codex 请你拍板的那三件）

### 1. 版本保命 —— 最高优先，且要把"提交"和"批准"拆开

- **事实**：P1.6 已提交并打了 tag `p1-readonly-done`；但此后整个 P2（79 文件，含 V4_27/V4_28）全部飘在未提交。而**这两个迁移已经真实改了 wms_db 的结构**——源文件一旦丢失或被 `git checkout` 冲掉，数据库就成了"有结构、无来源"的孤儿，Flyway 校验也会错乱。
- **我的判断**：Codex 把"提交代码"和"批准合并推远程"绑在一起等你验收，这两件应该拆开——
  - **保命提交（本地，立即做，不需要等验收）**：把工作存下来，让 DB 与源码重新对齐。
  - **批准 + 推远程（等验收通过再做）**：这才是需要你点头的动作。
- **建议指令**：让 Codex 现在就按模块分批本地提交（出库 / 盘点+校正 / 仓库库位 / 移动PWA / IAM / 销售分析 各一提交），排除本机文件（settings.local、launch.json、临时产物），**先不推远程**。

### 2. DEPLOYMENT.md 审核结果 —— 通过，可作首次上线依据

通读完毕，质量高：环境变量全集（含缺失即失败的强约束）、prod profile 关调试与 OpenAPI、静态同域托管步骤、Nginx 最小配置、Shopify 只读上线七步（明确"不申请任何 write scope"）、每日备份 + 季度恢复演练 + 回滚原则都在。

两处非阻塞小建议：
- 恢复演练的核对清单加一句"CONSUMER / CLIENT 分别计数"，便于日后核对双轨数据。
- 回滚原则补一句"V4_27/V4_28 这类**含数据回填**的迁移，前向修复前需先确认回填是否可逆"。

### 3. 真实数据验收的"鸡与蛋" —— 有安全的解法

- **卡点**：验"B2C 自动归档"需要 CONSUMER 数据，但 CONSUMER 只在 `retail_mode=ON` + 真实同步时才产生；而我们定了真店 retail_mode 默认关、验收前不开。
- **关键洞察**：**开 retail_mode 是安全的**——Shopify 侧是只读的，这个开关只决定"本地要不要建 CONSUMER 档案"，绝不会写店铺。因此可以这样闭环验收：
  1. 临时把真店 retail_mode 开启；
  2. 手动同步一轮（只读拉真实订单）→ 观察是否正确按 customer.id/邮箱 建出 CONSUMER、收货快照 8 列是否落库、订单是否 PENDING_APPROVAL；
  3. 验完把测试产生的订单 **VOID**（不审批 → 零库存影响），retail_mode 按你决定保留或关回。
- **发货登记验收独立**：挑一张既有订单，用运单接口登记一条→改一条→作废一条，验证一单多运单与审计留痕，不依赖 CONSUMER。
- 这部分我可以像前几轮一样**亲自真机走查**。

## 四、被忽略的最大验收债：八个模块无人点过

ACCEPTANCE_NOTES 里每个 P2 模块都写着"浏览器自动化内核无法启动……保留人工视觉验收项"。翻译过来：**出库、盘点、紧急校正、仓库库位、移动 PWA、IAM、销售分析、客户采购分析——八个模块界面结构测过、真机没人走过**，全部挂"待用户验收"。这是当前最大的隐性债。

建议真机验收就按这八个模块逐一走查，我来做。移动 PWA 需在 430px 窄屏 + 断网场景单独验（它声明离网时停用全部库存写操作）。

## 五、下一批排期：我对那 10 项的重排

Codex 建议先做采购单"添加商品"。方向对——那是你日常建单的实际拦路石。但我按**纠错性 > 易用性 > 信息架构 > 架构级**重排，并把 Codex 列在第 3、实则该提级的一项拎出来：

### Tier 0 · 立即（非功能开发）
提交保命 + 真机验收 + 版本收尾（见第三节）。

### Tier 1 · 纠错（有真实数据/流程风险，优先于一切易用性优化）
- **商品停用后端拦截缺失（UI-REVIEW-002）** —— 我独立证实了：`SalesSubmissionService` 手工建单路径**完全没有停用校验**，而渠道补单路径反而查了 `sku.getEnabled()`。也就是说**界面显示"停用"，手工销售单却仍能把停用商品加进去**，自动化路径比手工路径还严。这是**静默的数据完整性漏洞，不是 UI 问题**，严重度我判定 ≥ 采购单 bug。需要在统一服务层给销售/入库/分配补上停用拦截。
- **采购单"添加商品"（UI-REVIEW-006）** —— 确认损坏，日常建单的实际拦路石。
> 这两项并列做。

### Tier 2 · 易用性
采购多商品表格扩展性（007）、销售/采购 Excel 模板机制（003/005，外部模板优先+内置兜底）、销售订单渠道/状态/履约梳理（004，先只梳理展示层不动状态机）。

### Tier 3 · 信息架构（需先设计再动手）
商品管理 vs 库存查询边界（001）、渠道店铺自定义名称 + 渠道链路重构（008/009）、驾驶舱二期利润与趋势（010，一期销售概览已交付）。
> **利润口径只有你能拍**：不能用销售额减主数据价格粗算，需先定成本法（移动平均 / 批次实际成本）、退货折扣税费运费汇率口径。这是 010 的前置输入。

### Tier 4 · 架构级
多仓 SKU 经营策略（ARCH-011，**前置=先消除 minStock/safetyStock 语义重叠**）、Localization 时区口径（ARCH-012，现存 ReportSummaryScheduler 硬编码 Asia/Shanghai 与预测用 Europe/London 打架）、**Flyway 零初始化基线**。
> Flyway 基线是我在 V4_5_1 那次查明的老账——迁移链自 V2 起就不自包含（引用 Hibernate 早期建的表），纯空库跑不起来。这是 SaaS 化前必过的闸门，且**每加一个迁移债越滚越大**，建议趁链条还没更长排进 Tier 4 靠前，别拖到 SaaS 前夜。
