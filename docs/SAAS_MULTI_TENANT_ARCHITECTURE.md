# BCWMS SaaS 多租户架构基线

状态：已确认的产品与后端架构决策
更新日期：2026-08-13

## 1. 目标体验

BCWMS 采用与 SalesBinder 可观察流程一致的公司开户体验：

1. 用户从官网进入统一入口 `https://app.bcwms.com`。
2. 在统一入口选择免费版或 30 天试用版并验证邮箱。
3. 用户填写公司名称、管理员资料、密码和公司网址简称 `slug`。
4. 后端创建公司、公司域名、订阅、首位管理员与默认业务配置。
5. 注册完成后使用一次性交接码跳转至 `https://{slug}.bcwms.com`。
6. 首位注册用户自动成为该公司的 `TENANT_ADMIN`。

域名边界：

| 地址 | 用途 |
| --- | --- |
| `https://app.bcwms.com` | 注册、邮箱验证、统一登录入口 |
| `https://platform.bcwms.com` | 平台开发者管理后台 |
| `https://{slug}.bcwms.com` | 公司业务工作台 |

`slug` 是公司选择的网址简称。例如 `slug=mingze` 对应
`https://mingze.bcwms.com`。它只负责定位公司；业务数据始终以不可变的
`company_id` 归属公司。

## 2. 已确认的决策

- 数据采用共享 PostgreSQL；控制面与租户业务面逻辑隔离。
- 产品界面对租户称“公司”，后端技术概念称 `tenant`，现有业务租户键继续使用
  `company_id`。`tenants.id` 是 `company_id` 的权威来源。
- 首位注册用户直接成为 `TENANT_ADMIN`。
- 第一版一个邮箱只能属于一个有效公司，但身份与公司成员关系必须解耦，为未来多公司保留兼容性。
- 同时提供免费版和 30 天试用版。
- 30 天试用版开放所有服务功能；“全功能”不等于“无限容量”，防滥用容量上限另行确定。
- 免费版永久有效；`1 个用户 / 1 个仓库 / 100 个 SKU` 作为首版候选范例，最终额度待确认。
- 公司 `SUSPENDED` 与 `CLOSED` 分开；只有 `CLOSED` 启动当前暂定为 30 天的数据清理倒计时。
- 平台超级管理员永久拥有跨公司读取和导出权限。
- 平台修改或删除公司数据必须取得该公司的明确许可。
- 平台账号不出现在公司用户列表；平台访问审计只保存在平台控制面，不向公司展示。

## 3. 套餐、功能与容量

套餐模型必须把“功能资格”和“资源配额”分开：

- `entitlements`：某项功能是否开放，例如库存、采购、销售、集成、报表。
- `quotas`：资源数量上限，例如用户、仓库、SKU、集成数量、文件容量。

第一版套餐规则：

| 套餐 | 有效期 | 功能资格 | 容量配额 |
| --- | --- | --- | --- |
| `FREE` | 永久 | 基础功能范围待确认 | 待确认；候选范例为 1 用户、1 仓库、100 SKU |
| `TRIAL` | 30 天 | 所有服务功能 | 防滥用上限待确认 |

注册时选择 `FREE` 的公司直接进入免费版；选择 `TRIAL` 的公司进入 30 天全功能试用。
试用到期不关闭公司、不启动删除倒计时。到期后是降级到 `FREE`、转为受限只读，还是仅提示
升级，仍待确认；数据不得因试用到期直接删除。

公司生命周期与订阅生命周期必须独立：

```text
公司：PROVISIONING -> ACTIVE -> SUSPENDED -> ACTIVE
                              -> CLOSED -> PURGE_PENDING -> PURGED

订阅：TRIALING -> 到期策略待确认
      FREE / ACTIVE -> PAST_DUE / CANCELED / EXPIRED
```

## 4. 公司暂停、关闭与清理

| 公司状态 | 访问策略 | 数据策略 |
| --- | --- | --- |
| `PROVISIONING` | 不开放业务访问 | 正在初始化 |
| `ACTIVE` | 正常访问 | 正常保留 |
| `SUSPENDED` | 只开放账户、续费或申诉入口 | 保留且不启动删除倒计时 |
| `CLOSED` | 禁止业务访问 | 当前暂定保留 30 天，可恢复 |
| `PURGE_PENDING` | 禁止访问 | 等待清理任务 |
| `PURGED` | 不可访问 | 在线业务数据已清理；保留最小公司墓碑记录以维持平台审计链 |

按当前暂定策略，进入 `CLOSED` 时设置 `closed_at` 和
`purge_due_at = closed_at + 30 days`。备份介质中的
数据保留期由独立备份政策规定，不能承诺与在线数据同时物理消失。

## 5. 单邮箱单公司与未来兼容性

第一版采用“一个邮箱只能加入一个有效公司”，以降低公司切换误操作、席位计费、通知归属、
离职撤权和审计复杂度。但数据模型不把邮箱永久锁死在公司用户表中：

```text
user_identities
  id
  normalized_email       全局唯一
  password_hash
  email_verified_at
  security_version

tenant_memberships
  identity_id
  company_id
  tenant_user_id
  status
```

第一版通过数据库策略限制一个身份最多存在一个有效成员关系。未来若开放多公司，只需放宽该
策略并增加公司选择页面；密码、邮箱验证、MFA、租户角色和 JWT 结构无需推翻。

保留多公司能力的业务理由包括：

- 集团或控股公司管理多个法人主体；
- 3PL、外包仓、代运营团队服务多个客户；
- 会计、审计、实施顾问需要进入多个公司；
- 加盟、区域公司以及员工跨公司兼岗；
- 并购和公司迁移期间需要一段重叠期；
- 同一自然人同时拥有生产公司、培训/沙箱公司或多个经营主体。

未来开放后，一套邮箱、密码和 MFA 可对应多个成员关系，每家公司仍拥有独立角色和撤权记录；
每次登录签发的 JWT 仍只绑定一个 `company_id`，不能在一次会话中跨公司读取数据。

## 6. 身份与权限边界

身份分为三类：

- `PLATFORM`：平台开发者与运维账号，存储在 `platform_users`。
- `TENANT`：公司用户，首位用户为 `TENANT_ADMIN`。
- `SYSTEM`：定时任务、Webhook、消息消费者等非人类主体。

平台权限：

| 操作 | 永久权限 | 公司许可 |
| --- | --- | --- |
| 读取、搜索、统计 | 开放 | 不需要 |
| 导出 | 开放 | 不需要 |
| 修改 | 不永久开放 | 必须取得许可 |
| 删除 | 不永久开放 | 必须取得许可 |

修改和删除许可至少记录 `company_id`、操作类型、资源范围、批准人、批准时间和撤销时间。
当前安全实现还要求许可带到期时间，避免一次授权永久有效；默认有效期与资源粒度仍待确认。

平台永久读取/导出已实现为独立平台面 API：

- 只能通过 `https://platform.bcwms.com/api/platform/companies/{companyId}/...` 使用平台 JWT；
  平台 JWT 不能访问公司子域，也不能伪装公司用户。
- `PLATFORM_TENANT_READ` 只能分页读取；`PLATFORM_TENANT_EXPORT` 只能创建和下载导出；
  `PLATFORM_SUPER_ADMIN` 同时拥有二者。修改、删除不在这些 API 中。
- 支持用户、角色、仓库、库位、商品、SKU、库存、批次、客户、供应商、采购单、销售单、
  入库单、出库任务、盘点和已脱敏集成概况。数据集由服务端固定定义，不接受任意 SQL、表名或字段名。
- 密码、密码哈希、JWT、验证码、一次性交接码、API Key、Client Secret、Access Token、
  数据库凭证和加密密钥永不进入读取响应或导出文件。
- 导出采用后台任务生成 UTF-8 CSV 的 ZIP，包含固定 manifest、SHA-256 摘要和记录数；
  文件 24 小时后由平台任务删除，追加式审计元数据永久保留。
- 每次目录读取、数据读取、导出申请、导出完成/失败和下载都只写入控制面的
  `platform_audit_logs`。公司端没有相关 Controller、数据集、通知或查询入口，平台读取也不更新
  公司业务行，因此不会在公司业务操作记录中产生更新时间或操作人痕迹。
- 这里的“公司端无感”仅指产品与业务数据层不展示、不通知、不留业务修改痕迹；不能承诺数据库
  运维监控、网络监控、备份或依法进行的独立合规审计在现实中绝对无法发现平台访问。

## 7. 请求与租户解析

请求必须先解析 Host，再认证 JWT：

```text
Host -> TenantResolutionFilter -> TenantContext
     -> JWT authentication -> company_id 一致性校验 -> authorization -> business service
```

- `app.bcwms.com` 只允许注册、验证和统一入口 API。
- `platform.bcwms.com` 只允许平台 API。
- 只有已登记的 `{slug}.bcwms.com` 才允许公司认证和业务 API。
- 不接受请求参数或任意请求头直接指定 `company_id`。
- 公司 JWT 的 `company_id` 必须与 Host 解析结果一致。
- 未知 Host、畸形 Host、多级子域和保留 slug 默认拒绝。
- 注册完成跨子域时使用短时、单次 opaque handoff code；JWT 不放在 URL，也不使用跨全部子域的共享认证 Cookie。

## 8. 共享库隔离原则

- 控制面表 `tenants`、`platform_users` 不继承业务 `BaseEntity`，也不带 `company_id`。
- 每张租户业务表必须有 `company_id NOT NULL`。
- 查询、更新和删除必须使用 `company_id + resource_id/business_key`。
- 唯一约束和高频索引以 `company_id` 为首列。
- 缓存、锁、文件、Outbox、Webhook、报表、幂等键和定时任务全部使用公司命名空间。
- 应用层 `TenantContext` 是第一道边界；PostgreSQL RLS 是数据库兜底边界。
- 无租户上下文的普通业务写入必须失败，不能继续使用 `company_id=1` 静默兜底。

## 9. 实施阶段

1. 创建自包含 Flyway 基线，并把现有数据登记为默认公司 `id=1`。
2. 建立公司、公司域名、身份、成员关系、注册、验证、套餐、订阅和平台账号控制面。
3. 建立 Host 解析、`TenantContext`、公司 JWT 和平台 JWT。
4. 完成邮箱验证与幂等公司开户编排。（已完成）
5. 将用户、角色、权限和全部业务 Repository 改为公司范围查询，并租户化缓存、任务、
   Webhook 与报表。
6. 启用共享库 PostgreSQL RLS，并完成文件、消息等非 HTTP 链路的数据库兜底隔离。
7. 建立平台永久读取/导出以及经公司许可的修改/删除流程。

## 关闭后数据清理

公司进入 `CLOSED` 后，当前暂定保留在线数据 30 天；`SUSPENDED` 不会启动该倒计时。
到期任务先将公司改为 `PURGE_PENDING`，再在匹配的 PostgreSQL RLS 公司上下文内清除业务数据、
公司域名、成员关系、订阅、注册和登录交接数据及残留导出文件。任务带租约并可安全重试，
失败不会把公司误标记为已清除。完成后保留匿名化的 `PURGED` 公司墓碑、平台访问审计、
清理任务和追加式清理审计；公司业务审计随业务数据一并清除。
8. 用至少两家公司和一个平台身份完成端到端串租与越权测试。

当前代码已完成第 2 项的控制面骨架、第 3 项的 Host 解析、请求入口矩阵、`TenantContext`、
公司 JWT 与平台 JWT 分离，并完成第 5 项和第 6 项中的数据库 RLS 边界：

- 用户、角色、权限、权限申请和用户仓库均使用公司范围查询与公司命名空间缓存；
- 全部租户业务实体使用 Hibernate `@TenantId`，普通 Repository 查询自动携带公司边界；
- 主键查询改用公司范围 Criteria 查询，避免 `EntityManager.find` 绕过租户过滤；
- 库存、分类、角色继承和报表等原生 SQL 显式绑定 `company_id`；
- Shopify Webhook 先用唯一店铺路由找到公司、校验 HMAC，再进入该公司的上下文处理业务数据；
- 报表、渠道同步和 Shopify 对账定时任务逐个枚举 `ACTIVE` 公司，并在每次执行后清理上下文；
- 双公司同业务键、跨公司主键读取、后台任务上下文清理和 Webhook 路由均有自动化测试。
- 每个 Spring 数据库事务都会用服务端解析出的公司上下文设置事务级
  `app.company_id`；事务结束后该值不会残留到连接池；
- V4.52 对全部租户业务表启用并强制执行 PostgreSQL RLS。缺少公司上下文时返回零行并拒绝写入，
  公司 A 的事务无法读取、修改、删除或新增公司 B 的数据；
- 生产启动会拒绝 PostgreSQL `SUPERUSER` 或 `BYPASSRLS` 账号，平台读取也必须显式进入目标公司
  上下文，不能通过数据库旁路跨公司读取；
- Webhook 在尚无公司上下文时只查询最小化的控制面路由，验签并解析公司后才访问受 RLS 保护的
  集成配置和业务数据。
- 公共注册支持 FREE/TRIAL 选择、SMTP 邮箱验证码、10 分钟有效期、5 次尝试、60 秒重发间隔和
  单邮箱每日 10 次上限；验证码只存带服务器 pepper 的 SHA-256 哈希；
- 注册完成使用分阶段事务状态机创建公司、一级子域、身份、公司成员、内部用户、
  `TENANT_ADMIN` 和订阅；数据库唯一约束与事务锁保证重复请求不会重复开户；
- 开户成功只返回 60 秒有效的一次性 opaque 交接码，数据库只存哈希；交接码必须在对应公司
  Host 消费，且只能成功一次，不会通过 URL 传递 JWT。
- 开户响应把交接码放入 `https://{slug}.bcwms.com/#/session/handoff?code=...` 的 URL fragment；
  fragment 不发送给反向代理或后端。公司页面载入后立即清除地址栏中的交接码，再通过
  `POST /public/v1/session-handoff/consume` 原子兑换公司 JWT；数据库悲观锁保证并发请求也只能
  成功一次。兑换得到的会话仅保存在该公司子域自己的 `localStorage`，不会共享给其他公司子域。
- 首位注册用户兑换后以 `TENANT_ADMIN` 进入公司仪表盘；前端将该角色视为公司内全权限，平台
  身份与公司身份仍使用不同 JWT，不能通过此接口互换。

公司 JWT 的 `company_id` 已在查询用户和权限前与 Host 强制比对；同名角色的双公司隔离、
跨公司角色分配拒绝和缓存公司边界已有自动化测试。V4.51 增加了渠道店铺的全局唯一活动路由、
公司范围 Webhook 幂等约束和相应索引。

运行时多租户开关仍由启动保险丝锁定。平台访问 API、文件与消息链路及反向代理
通配子域完成前，不得开启生产多租户流量。现有 Flyway 历史链也尚非空库自包含，第 1 项仍需
单独完成。当前已落库关闭截止时间和清理状态模型，实际按 `company_id` 清理全部业务表
的任务尚未实现，因此不能宣称 30 天后已经自动删除。

当前实现状态还包括：V4.50 控制面迁移已在 PostgreSQL 18 临时隔离 schema 中验证通过；但完整
历史 Flyway 链仍依赖早期 `users` 等表，正式升级前必须在生产结构副本上再做一次全链演练。
