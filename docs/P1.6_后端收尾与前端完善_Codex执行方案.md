## Step 1：对账补单 bug 修复 + 外部订单数据库级防重

### 1.1 markFailed 误伤修复

**现象**：`ShopifyReconciliationService.repair` 的 catch 块对任意传入的 eventId 调 `rawEventService.markFailed`。若调用方误传一个非对账来源的事件 ID（例如某条已 PROCESSED 的 webhook 报文），该无关记录会被改成 FAILED，污染审计状态。

**修法**：`requireRepairCandidate` 校验不通过的（不存在 / 渠道·来源·类型不符）只记入返回结果 items（status=BLOCKED），**不得**调 markFailed；只有真正的对账候选事件在后续处理失败时才标 FAILED。

**护栏测试**：传入一个 webhook 来源的事件 id → 断言该事件状态不变、结果中标记 BLOCKED。

### 1.2 外部订单防重下沉到数据库

**现象**：`sales_orders.external_order_id` 目前只有普通索引（V3_9），防重全靠程序查询（`findByExternalOrderId`）。Webhook 与轮询同时到达同一订单时存在并发窗口，可能创建重复订单。

**修法**：迁移 `V4_23__External_Order_Dedup.sql`：

- 部分唯一索引：`UNIQUE (company_id, channel, external_order_id) WHERE external_order_id IS NOT NULL`
- 迁移前置检查：先跑重复数据检测 SQL（同 company_id+channel+external_order_id 计数 >1），有存量重复则迁移失败并报出重复单号，人工清理后重跑——**不得静默删数据**
- 程序层查询防重保留（提前给出友好错误）；数据库约束是并发兜底，唯一约束冲突映射为已有的 `SHOPIFY_ORDER_ALREADY_SYNCED` 语义

**门禁**：新测试（含并发语义：第二次落库撞约束不产生脏数据）+ 全量绿。

## Step 2：客户双轨制（本轮核心，方向已由用户确认：轻量建档）

### 2.1 决策背景与边界（已定稿，不得偏离）

- 系统主场景是 Client（企业客户）供应链：客户 = 受管控主数据（信用/账期），**现有"渠道单只匹配既有客户"的严格逻辑对企业渠道原样保留**。
- C 端零售渠道（自营 Shopify 店）按行业惯例（Dynamics 365 async customer / NetSuite 连接器模式）**自动创建轻量客户档案**。挂靠账户方案已否决。
- **自动建档只属于系统自动同步链路（sync/webhook）**。人工对账补单（repair）维持原安全边界：只能匹配既有客户、创建待审批订单，**不能创建客户**——补单遇到不存在的客户时标 BLOCKED 并给出原因，操作员先按正常主数据流程建客户再补单。V4_22 权限描述（"cannot create customers"）保持准确，无需修改。
- 存储成本已核算过（约 1KB/档案），不构成约束。

### 2.2 数据库迁移 V4_24__Customer_Dual_Track.sql

- `customers` 加列（V4_24 历史落库形态，后续已由 V4_26 将 `B2B` 前向迁移为 `CLIENT`）：
  - V4_24：`customer_type VARCHAR(20) NOT NULL DEFAULT 'B2B'`，CHECK IN ('B2B','CONSUMER')
  - V4_26 现行值：`customer_type VARCHAR(20) NOT NULL DEFAULT 'CLIENT'`，CHECK IN ('CLIENT','CONSUMER')
  - `source VARCHAR(20) NOT NULL DEFAULT 'MANUAL'`，CHECK IN ('MANUAL','CHANNEL')
  - `external_customer_id VARCHAR(64)`（渠道侧客户标识，Shopify `customer.id`），部分唯一索引：`UNIQUE (company_id, external_customer_id) WHERE customer_type='CONSUMER' AND is_deleted=false`
  - `normalized_email VARCHAR(100)`（小写+去首尾空格），存量数据回填；部分唯一索引：`UNIQUE (company_id, normalized_email) WHERE customer_type='CONSUMER' AND is_deleted=false`（B2B 不强制唯一，历史数据可能共用邮箱）
- `integration_configs` 加列：`retail_mode BOOLEAN NOT NULL DEFAULT false`——**迁移不得为任何存量配置打开**（含 Bubble Crush UK id=1），测试通过后由人工在界面启用
- `sales_orders` 加**当次收货快照列**（发货作业和地域分析的数据基础）：`consignee_name` / `consignee_phone` / `ship_address1` / `ship_address2` / `ship_city` / `ship_province` / `ship_zip` / `ship_country_code`（VARCHAR，均可空）——快照属于订单履约必需信息，不回写客户主档
- 注意：PostgreSQL 用 `COMMENT ON COLUMN` 单独语句；测试库不走 Flyway（ddl-auto），**实体改动必须与迁移同批完成**

### 2.3 服务逻辑

**同步链路（sync/webhook）的客户解析**，行为由店铺配置决定：

- `retail_mode=false`（默认，企业渠道）：维持现状严格匹配，匹配不到 → FAILED 报文留底
- `retail_mode=true`，按优先级：
  1. **报文带 `customer.id`** → 按 `external_customer_id` 查 CONSUMER 档案：命中 → 复用（顺带补全 normalized_email 若变更）；未命中 → 走第 2 步邮箱匹配，仍未命中则自动建档
  2. **邮箱后备匹配**（访客结账无 customer.id 时的主路径）：归一化邮箱查启用客户——命中唯一一条（CONSUMER 或 CLIENT）→ 复用；**命中多条 CLIENT → 不得自动猜测，标 FAILED/BLOCKED 留人工裁决**；未命中 → 自动建档
  3. **自动建档**：`customer_type=CONSUMER`、`source=CHANNEL`、字段仅 email / normalized_email / external_customer_id / name（取报文姓名）/ code 自动生成（如 `C` + 序列）、`credit_limit=0`，不参与 B2B 主数据治理
  4. 报文既无 `customer.id` 也无邮箱 → FAILED（身份锚点缺失，不建无名档案）
- **repair 补单**：只做匹配（同样的 1→2 匹配逻辑，但**任何未命中/多义都 BLOCKED，绝不建档**）
- `retail_mode` 的修改入口仅 SUPER_ADMIN（店铺配置 API 已是 admin 权限，确认覆盖此字段即可），配置响应中明示当前状态
- 收货快照：从报文 `shipping_address` 提取落到订单快照列；手工单表单允许选填
- **验证风控不误伤**：渠道单强制 PENDING_APPROVAL，确认 `checkRiskControl` 对 credit_limit=0 的 CONSUMER 不会抛异常阻断创建（人工审批环节把关）
- **个人信息边界（如实表述）**：客户主档只存邮箱/姓名/渠道标识；订单快照存当次收货信息（履约必需，合同履行的合法基础）；`channel_raw_events` 原始报文含完整个人信息，**以订单处理与审计为目的保留**，留存期限与归档/匿名化策略记入路线图（本轮不做，但不得在文档或代码注释里声称"系统只保存最少个人信息"这种与事实不符的话）

### 2.4 测试要求

- retail off：严格匹配行为回归不变
- retail on：customer.id 命中复用 / customer.id 未命中+新邮箱建档 / 访客结账邮箱唯一命中复用 / **邮箱命中多条 CLIENT → BLOCKED 不建档不猜测** / 无任何身份锚点 → FAILED
- repair：客户不存在 → BLOCKED 且不建档（护栏测试）
- 建档路径创建的订单仍是 PENDING_APPROVAL、零库存副作用（复用既有护栏测试模式）
- 收货快照字段落库断言

**门禁**：全量绿。
