- 交付状态：开发和自动化回归已完成；尚未合并、部署或执行生产数据迁移。

## 1. 本阶段交付结果

P0-02 已将采购到货、其他入库和库存落账收敛为统一收货链路。租户不再从采购页面或旧入库接口直接修改库存；所有实收数量必须通过收货任务提交，并由同一事务完成批次、库存流水、业务单据和事件更新。

最终主流程如下：

1. 采购员创建采购草稿，并将每一采购行的全部数量分配到目标仓库；同一采购行允许按数量拆到多个仓库。
2. 采购单提交后，普通租户按 `NONE` 模式直接生效；启用 `SIMPLE` 的高端租户进入采购审批。
3. 采购单生效后，系统按目标仓库生成 `WAITING_SHIPMENT` 收货计划。此时仓库可提前维护优先级、预计时间段、收货人员或班组、月台或作业区及仓库备注。
4. 采购员可在采购页面使用“确认发货”快捷操作，由系统原子创建并确认 ASN；复杂业务也可进入 ASN 草稿管理，编辑后再确认。
5. 已确认 ASN 生成统一收货任务。仓库只看到完成作业所需的采购单号、仓库、商品、数量及作业信息，不展示供应商、价格、合同条款、承运商、运单号或 ASN 编号。
6. 仓库人员按登录账号和被分配仓库访问任务，在提交时为每条实收记录确认库位、数量，以及按 SKU 规则要求的批次和效期信息。
7. 每次提交全部原子执行：任一行失败，批次、库存流水、收货事件、任务、ASN、分仓数量和采购状态全部回滚。
8. P0-02 收货成功后库存直接进入 `AVAILABLE`。部分到货可继续分批收货；不再到货的剩余数量由采购侧按租户策略直接说明原因关闭，或提交审批后关闭。

## 2. 采购治理与 ASN

- 采购单草稿支持完整的多仓数量分配，并在提交前校验每行分仓合计等于订购数量。
- 采购单首次保存成功、分仓保存失败时，前端会进入已保存草稿的恢复编辑态；重试更新原单，不重复创建采购单。
- 删除采购行前会先锁定并清理尚未执行的分仓记录；已有执行历史时拒绝删除。
- 采购审批模式和短收余量关闭模式是两个独立的租户治理开关：
  - 采购审批：`NONE` / `SIMPLE`。
  - 短收关闭：`DIRECT_WITH_REASON` / `APPROVAL_REQUIRED`。
- 一张采购单允许多张 ASN；一张 ASN 只对应一个采购单和一个目标仓库，并可包含多个 SKU。
- ASN 累计发货数量不得超过对应分仓的可发数量。
- ASN 草稿支持带版本号更新，避免多人编辑互相覆盖。
- 已确认且尚未收货的 ASN 可取消，或通过“纠错”将原单取消并克隆为新草稿；原记录保留审计链路。
- ASN 一旦发生收货，不允许修改或取消，只能处理剩余未收数量；采购单是否闭环由实收和已关闭余量共同推进。

## 3. 统一收货与库存安全

- 新建统一收货计划、收货任务、任务明细、收货事件和收货事件明细模型。
- 收货任务列表的仓库范围已下推至数据库查询；仓库员工没有分配仓库时直接返回空列表，不执行租户全量查询。
- 任务库位接口仅返回任务所属仓库内启用的安全字段：库位 ID、编码和名称。
- 收货客户端不接受操作人字段，操作人 ID 和名称只从当前登录会话取得。
- 收货写入要求 HTTP 幂等键；重复请求返回同一结果，不重复增加库存。
- 单次提交允许多条任务明细，每条明细包含任务行、库位、数量及可选批次信息；后端支持同一任务行分批、分库位提交。
- 防止超收，并同步推进收货任务、ASN、采购分仓、采购明细和采购单状态。
- 已移除采购直接收货、采购回退、旧入库直接收货及客户端指定操作人的旧入口。

## 4. 其他入库申请

原 `/inbound` 页面已重构为“其他入库申请”，不是调拨功能，也不再直接落账。

- 功能默认关闭，由租户管理员单独开启。
- 管理权限为 `other_inbound:manage`；实际收货权限为 `receiving:execute`。
- 管理员可配置允许使用的其他入库业务类型。
- 申请确认后同样生成统一收货任务，库存只能通过统一收货落账。
- 开关关闭后禁止新建、编辑和确认，但保留历史及在途申请的查询与取消、关闭、作废等终结操作，避免已有流程悬空。

## 5. SKU 效期管理

- SKU 增加“是否启用效期管理”设置。
- 启用时，收货必须填写生产日期和有效期，并校验日期关系。
- 未启用时允许留空，不要求普通无效期商品填写虚假日期。
- 收货任务直接携带该 SKU 的效期管理标记，仓库端不需要额外取得全量商品主数据权限。

## 6. 权限、隐私与接口契约

- 采购、ASN、收货计划、收货执行、其他入库及治理开关使用分离权限。
- 仓库任务和计划响应经过专用 DTO 映射，不暴露供应商、成本、条款、物流或 ASN 信息。
- 为采购和其他入库分别提供域内 SKU、仓库参考接口，避免前端因填单而取得宽泛主数据权限。
- OpenAPI DTO 使用唯一业务命名；已重新导出 `docs/frontend/openapi.json` 并生成 `frontend/src/api/schema.d.ts`。
- 已删除旧 `/api/inbound-orders`、采购确认收货、采购回退等 OpenAPI 路径。

## 7. 数据库迁移

本阶段新增且不存在版本号冲突的迁移：

- `V4_74__Purchase_ASN_And_Unified_Receiving.sql`
- `V4_75__SKU_Expiry_Management.sql`
- `V4_76__Controlled_Other_Inbound_Applications.sql`
- `V4_77__Purchase_Remainder_Closure_Approval.sql`

旧数据迁移遵循“建立新流程映射，但不重放库存”的原则，防止已有库存再次入账。上线前仍必须在隔离的 PostgreSQL 副本中使用真实旧数据执行一次 Flyway 彩排，并核对迁移前后库存总量、单据状态和异常记录。

当前开发数据库角色不具备创建隔离数据库的权限，因此本次没有把“真实旧数据 Flyway 彩排”误报为已完成，也没有对现有数据库进行试探性迁移或库存重放。
