## 已确认业务规则

- 第一版“角色”和“岗位权限包”是同一业务对象、同一张 `sys_role` 表；“岗位权限包”是面向用户的产品名称。
- 不新增 `PermissionPackage` 等平行实体，避免角色、权限包两套授权来源和迁移成本。
- 用户可以拥有多个岗位权限包，但一次登录会话只能激活一个；请求鉴权只使用当前激活包及其继承权限。
- 管理员给员工分配的是已经定义好的岗位权限包，不能直接给单个员工随意拼接 `inventory:adjust` 等底层权限。
- 自定义岗位权限包可以从空白创建并逐项勾选权限，也可以复制已复核模板形成独立快照；系统默认包与自定义包必须能区分。
- `IAM` 管理和库存调整属于独立关键权限，不因普通仓库岗位自动获得。
- 权限判断以后端为准；前端隐藏菜单和按钮只是体验层，不能替代后端鉴权。
- 任何角色、权限、密码或账号状态变化必须能够使受影响用户的旧令牌立即失效。
- 禁用角色不再贡献任何直接或继承权限，并停止沿该禁用角色继续向上继承。
- 岗位权限包复制不得修改源包，也不得自动给任何用户分配新包。
- 岗位权限包复制采用独立权限快照，不建立与源角色或其父角色的持续继承关系。
- 系统内置内容分为“普通业务模板”和“受保护特权角色”；`SUPER_ADMIN` 与 `SECURITY_ADMIN` 均属于受保护特权角色。
- IAM 管理及系统控制保留权限不得复制、导入或手工分配给普通自定义角色。
- 新自定义权限包的 `description` 是必填用途说明；适用人数不影响授权，实际人数实时统计；风险说明由权限风险等级计算，包含高风险权限时另行填写操作理由。
- 复制预览必须显示有效权限明细和 `NORMAL/HIGH/CRITICAL` 统计；服务端提交时重新计算并比较指纹，源模板变化时返回冲突并要求重新确认。
- 只有 `NORMAL` 时执行普通确认；包含 `HIGH` 时要求业务理由、风险勾选和输入新权限包编码；包含 `CRITICAL` 或不可分配/保留权限时禁止复制。
- 复制审计记录操作人、源/目标角色快照、高风险权限、理由和指纹；审计记录不得因后续删除自定义角色而丢失。
- 新复制包默认 `DRAFT + DISABLED`，不自动启用、不自动分配用户；批准也不会自动启用。
- 空白新建包同样默认 `CUSTOM + DRAFT + DISABLED`，允许零权限起草；只有勾选的可分配权限成为直接权限，不自动建立继承关系。
- 内置简易审批固定单级复核，不支持会签、多级、委托或加签；驳回必须填写修改意见并回到草稿。
- 普通风险可由同一名有权 IAM 管理员提交和复核；高风险必须由不同的超级管理员账号复核。`SECURITY_ADMIN` 可驳回高风险申请但不得批准。该规则是当前小公司模式的明确例外，后续正式审批模式需重新评审职责分离。
- 启用包不可原地编辑；新版本通过复制生成独立快照。只有已批准且启用的包可以分配给用户。
- 用户只要被分配 `WAREHOUSE_STAFF`，就必须同时分配至少一个启用仓库；可分配多个，重复仓库自动去重，移除该角色时仓库分配自动清空。
- 仓库范围仅取决于当前激活的 `WAREHOUSE_STAFF`；同一用户切换到 `WAREHOUSE_ADMIN` 等其他已授权角色后，不应用员工仓库范围。
- `WAREHOUSE_STAFF` 对跨多个目标仓库的入库单必须拥有全部相关仓库，不能因拥有其中一个仓库而操作整单。
- `V4_42` 不给历史员工自动推断或回填仓库；未分配仓库的历史 `WAREHOUSE_STAFF` 对入库、出库和盘点数据失败关闭，管理员必须先在用户角色分配中补选仓库。
- 权限申请仅由 `SUPER_ADMIN`、`SECURITY_ADMIN` 代目标用户发起；员工没有自助入口。仅可申请已启用、可分配的普通业务模板或 `CUSTOM + APPROVED + ACTIVE` 包，受保护特权角色不可申请。
- 批准申请只向目标用户新增所申请角色，保留其既有角色和默认角色；申请 `WAREHOUSE_STAFF` 时必须同时提交一个或多个启用仓库。
- 普通风险申请可由同一有权 IAM 管理员提交并复核；高风险申请必须由不同于申请人的另一名 `SUPER_ADMIN` 批准，`SECURITY_ADMIN` 只能驳回高风险申请。驳回意见必填；紧急撤销仍走直接收权。

## 2026-08-02 暂定治理备忘录

本节为用户确认的当前暂定规则。后续允许调整普通业务模板和新增受保护特权角色，但不得降低 `SUPER_ADMIN` 的固定保护级别。

### 当前运行态清点

- 受保护特权角色：`SUPER_ADMIN`、`SECURITY_ADMIN`。
- `SUPER_ADMIN` 是唯一具有代码级全局绕过的角色，可管理所有 IAM 身份。
- `SECURITY_ADMIN` 没有全局绕过，仅能管理普通用户、普通权限包和安全审计；不能授予或修改任何 `SUPER_ADMIN`/`SECURITY_ADMIN` 身份。
- 暂定普通业务模板：`GENERAL_MANAGER`、`WAREHOUSE_ADMIN`、`WAREHOUSE_STAFF`、`SALESPERSON`。
- `PURCHASER` 存在于前端角色模型但不在当前运行态数据库，待后续补齐后再纳入普通业务模板。
- 历史迁移中的 `CHAIRMAN`、`BUYER`、`SELLER` 作为旧名称处理，不再创建同义重复模板。
- 当前模板基线已收敛：`WAREHOUSE_STAFF` 为 8 项，`WAREHOUSE_ADMIN` 为 21 项，`GENERAL_MANAGER` 为 40 项，`SALESPERSON` 为 15 项。

### 当前落地策略

- `sys_role.system_category`：`BUSINESS_TEMPLATE`、`PRIVILEGED`，自定义角色为 `NULL`。
- `sys_role.import_allowed`：控制角色是否可作为复制/导入源。
- `sys_permission.risk_level`：`NORMAL`、`HIGH`、`CRITICAL`。
- `sys_permission.custom_assignable`：控制权限是否允许分配给自定义角色。
- `SUPER_ADMIN` 与 `SECURITY_ADMIN` 固定为 `SYSTEM + PRIVILEGED + import_allowed=false`；数据库约束和代码判断均不得允许降级。只有 `SUPER_ADMIN` 具有全局绕过。
- 自定义角色允许作为复制源；系统业务模板中仅已复核的 `WAREHOUSE_STAFF`、`WAREHOUSE_ADMIN` 为 `import_allowed=true`。
- `menu:system`、`system:admin`、`system:role:*`、`system:permission:*`、`system:user:*` 作为系统保留权限，固定为 `CRITICAL + custom_assignable=false`。
- 自定义角色不得直接获得系统保留权限，也不得通过继承受保护特权角色间接获得。
- 当前业务权限分级按业务影响而非 HTTP 方法确定；`V4_33__Classify_High_Risk_Permissions.sql` 将以下权限设为 `HIGH + custom_assignable=true`：`category:update`、`category:delete`、`global:view`、`inbound:receive_goods`、`integration:reconcile:repair`、`outbound:pick`、`product:status`、`product-sku:status`、`stocktake:count`、`supplier:update`、`supplier:delete`。
- 当前其余业务权限保持 `NORMAL`；`category:update` 和 `supplier:update` 因同时覆盖启用/停用操作暂列 `HIGH`，后续拆分权限颗粒度后可重新分级。

### 后续修改方式

- 普通业务模板完成权限校正和验收后，可通过受控变更把 `import_allowed` 改为 `true`。
- 新增特权角色时，将 `system_category` 设为 `PRIVILEGED`，并保持 `import_allowed=false`。
- 权限升级为系统保留权限时，必须先扫描并回收自定义角色中的既有授权，再推进受影响用户的安全版本使旧令牌失效。
- 已复制角色采用独立快照；源模板后续分类或权限变化不会自动改写既有复制结果。
- 第一版不开放在线修改特权分类和系统保留权限；此类变化只能通过版本化数据库迁移完成。普通模板维护入口后续另行评审。
- 用户已确认：当前先按上述暂定清单落地；后续需要修改受保护特权角色或普通业务模板时，回到本备忘录重新确认清单、保护级别、复制资格、审批要求和迁移/回收方案后再开发。

### 自定义权限包生命周期（当前已落地）

- 内置模板：`ROLE_PACKAGE_SIMPLE_APPROVAL`，`SYSTEM_DEFINED + ACTIVE + SIMPLE`，自身不可在线修改；`FORMAL` 模式只预留枚举和表结构。
- 状态流：复制/创建为 `DRAFT + DISABLED`；送审为 `PENDING_REVIEW + DISABLED`；批准为 `APPROVED + DISABLED`；显式确认后才变为 `APPROVED + ACTIVE`。
- 草稿允许修改名称、用途和直接权限；继承关系不允许在线编辑。送审后内容锁定，驳回必须有意见并返回草稿。
- 包含高风险权限时，送审理由必填且批准人必须为另一超级管理员；`SECURITY_ADMIN` 可驳回但不能批准。只有普通风险时，同一名有权 IAM 管理员可完成简易复核。
- 启用和停用均要求填写理由并输入权限包编码。停用始终允许作为紧急收权动作，并触发缓存清理和安全版本推进。
- 用户分配边界：系统角色继续要求启用；自定义包同时要求 `CUSTOM + APPROVED + ACTIVE`。批量替换先完整校验，避免删除旧分配后才发现新包不可分配。
- 全部生命周期动作写入不可变审计；受保护特权角色和系统业务模板不进入在线治理流程。
- 创建入口以“空白新建 + 复选框勾选”为当前最简主流程，模板复制保留为可选快捷方式；两种入口进入同一简易审批、启用和用户分配生命周期。

### 首版业务模板基线

- `WAREHOUSE_STAFF`：固定为 8 项移动收货、拣货和盲盘权限，保持最小作业范围，允许作为复制源。
- `WAREHOUSE_ADMIN`：包含上述 8 项权限，并增加商品、SKU、类目维护权限，共 21 项，允许作为复制源。
- `GENERAL_MANAGER` 与 `SALESPERSON` 已完成暂定精确基线并设为 `import_allowed=true`；前者包含受控业务审批，后者仅包含客户与销售日常维护，不包含审批、取消或作废。
- `V4_34__Repair_Business_Role_Templates.sql` 将两个已复核模板收敛到精确基线并推进受影响用户的安全版本；`V4_35__Role_Copy_Audit.sql` 建立不可变复制审计表；`V4_36__Decouple_Role_Copy_Audit_Foreign_Keys.sql` 保留审计快照且不阻塞自定义角色删除。
