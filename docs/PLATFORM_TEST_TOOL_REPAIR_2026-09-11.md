## 1. 修复内容

### 启动器生命周期

新增 `platform-process-lifecycle.mjs` 并接入专用 `platform-r2-database-batch.mjs`：

- 子进程 `exit` 与管道 `close` 分开记录。启动器已退出后，最多等待有限的输出排空时间；后台后代持有管道不会无限阻塞执行器。
- 数据库启动/停止命令的输出使用独立的新日志文件，不依赖继承的 Node 输出管道结束。
- 子进程超时/取消后，只尝试终止本次持有句柄的启动器；等待其退出也有上限。终止未确认会明确记录，不按进程名或端口批量结束进程。
- 启动成功必须同时满足：启动器正常退出、有限时间内数据库就绪、PID/启动时间/执行程序/精确目录/集群号/监听归属正确，以及只读 SQL 返回的数据库、用户、地址、端口、listen_addresses、目录和集群号匹配。端口存在或 exit 0 均不能单独判成功。
- 身份读取异常记为“未核实”，不能当成数据库启动失败。只有未观察到数据库且独立核实资源已不存在时，才可归类为启动失败。
- 启动失败/异常的收尾有独立预算，不等待失败的启动 Promise。收尾前再次核验身份，正常停止后还须核验进程、PID 文件、监听均已消失。
- 身份不符时拒绝停止该资源；收尾失败/超时如实保留，不伪报已关闭，也不自动换目标或再次强杀。
- 实际适配器中的进程、控制文件、监听及 SQL 检查均有单次超时，并传递取消信号；已超时的检查不能晚到后继续执行停止动作。

当前限时为：pg_ctl 自身启动等待 30 秒，命令外层 35 秒，启动器阶段总预算 37 秒；就绪核验 10 秒；收尾独立预算 45 秒，其中正常 pg_ctl stop 等待 30 秒。修复不是单纯延长旧超时。

实际状态分别保留 `READY`、`DATABASE_READY_EXECUTOR_FAILED`、`DATABASE_START_FAILED`、`DATABASE_READINESS_FAILED`、`STARTUP_UNVERIFIED`、`IDENTITY_REJECTED`，并独立保存 cleanup 状态。已启动数据库与执行器失败可以同时成立。

### 权限竞态角色夹具

`PlatformAccessGrantRoleRaceIntegrationTest` 仅调整 BeforeEach/AfterEach 及角色读取辅助方法：

- 读取 B 基线已有的运营管理员、安全审计员角色。
- 核验角色编码、有效 ID 及两个角色 ID 不同。

- 清理仅针对本用例创建的用户、用户角色关系、授权和租户，不创建或删除公共角色目录。
- 原竞态测试方法正文及权限断言不变；唯一约束、产品权限逻辑和数据库结构未改。

新增 `PlatformAccessGrantRoleFixtureTest`，用 mock 仓库验证以上夹具契约，不启动 Spring 或数据库。
