## 1. 目标模型（采纳原方案，两处修正）

三层：`Category`（数据库支持任意深度，当前前端限制两级）→ `Product`（SPU）→ `ProductSku`（库存/交易主体）。命名矩阵、字段职责、约束照原方案执行，仅修正：

1. **skuCode 生成规则**：历史 SKU 使用 `SKU` + 8 位旧 SKU ID；新 SKU 从数据库独立序列取号并沿用相同格式。`skuCode` 与 `barcode` 相互独立，创建后不可修改、删除后不复用。
2. **停用联动软化一处**：停用 ProductSku 时若存在未完结单据（未发货销售订单/未收货采购单），返回**警告需二次确认**而非硬阻断（业务常有"卖完就停"的清尾场景）。其余联动（停用 Product 先停全部 SKU 等）照原方案硬约束。

## 2. 引用审计雷区清单（Step 2 的输出模板）

`product_id → product_sku_id` 的遗漏点远不止外键列。**最险恶的陷阱：改名后 `products` 表仍存在但含义变了（SPU），任何漏改的引用不会报错，而是静默读错表。** 逐类审计：

| 类别 | 位置 | 说明 |
|---|---|---|
| JPQL 字符串 | 35 个 Service / 全部 Repository | grep `Product p`、`product.id`、`FROM Product`、`JOIN .*product` |
| **原生 SQL** | `ReportSummaryRefreshService`（报表刷新手写 SQL）、Flyway 历史迁移（不改，只确认新迁移后视图/物化逻辑仍对） | 原生 SQL 不受 IDE 重命名保护，必须逐条人工核 |
| JPA 注解 | `@JoinColumn(name="product_id")`、`@Table(name="products")` | 实体全扫 |
| **数据库内配置数据** | `sys_excel_template` 表（Excel 导入模板列定义）、`sys_permission` 表的 `resource_path`（如 `/api/products/**` 的权限行——URL 语义变了！） | 用 UPDATE 语句随迁移处理 |
| DTO / OpenAPI | 全部 `productId` 字段、`/api/products` 路径 | 重命名后重新生成 openapi.json |
| 历史 JSON 数据 | `domain_outbox.payload_json`、`channel_raw_events.payload` | **不改**（渠道报文是 Shopify 格式本就无关；outbox 旧键名容忍） |
| 渠道模块 | `channel_sku_mapping.product_id`、`ChannelSkuResolver`、`ShopifyIntegrationService`、`PendingSkuMappingService` | 全部 SKU 级语义，**只改名不改逻辑**；`ChannelSkuMapping.normalize()` 等资产原样保留 |
| 测试 | 988 个用例的实体引用、`TestSecurityConfig` 等 | 测试环境不走 Flyway（见 §4 注意事项） |
| 文档 | `docs/frontend/*.md`、`openapi.json` 快照 | Step 6 更新 |

外键列权威清单用以下查询生成（不要凭记忆）：
```sql
SELECT table_name, column_name FROM information_schema.columns
WHERE column_name = 'product_id' AND table_schema = 'public';
```
已知涉及（供核对）：inventory_batch、sales_order_items、purchase_order_item（**单数表名**）、inbound 明细表、stock_transactions、stocktake_items、backorder_line、inventory_reservations（如有）、channel_sku_mapping、旧 inventory 表（P4 待下线，本次只改名不下线）。

### Step 3：数据库迁移（V4_19，单文件，停机执行）
PostgreSQL DDL 是事务性的：单个迁移文件内失败整体回滚。顺序严格如下：
1. `ALTER TABLE products RENAME TO product_skus;`（先腾出名字）
2. `ALTER TABLE product_spu RENAME TO products;`
3. product_skus：`spu_id` → `product_id`；新增 `sku_code`（回填：barcode 优先，空则 SKU{id 补零}）；唯一约束 (company_id, sku_code)、(company_id, barcode)
4. products（原 spu）：`spu_code/spu_name` → `product_code/product_name`；新增 `category_id`（按映射清单回填，兜底"待整理"）；brand/enabled 等补列
5. 各业务表 `product_id` → `product_sku_id`（按审计清单逐表，纯元数据操作，瞬时）
6. 重建/重命名受影响的索引与外键约束名（PG 改名时约束自动跟随，但**约束名**保留旧名——统一改名以免误导后人）
7. `UPDATE sys_permission SET resource_path = ...`（/api/products/** 权限行按新语义调整 + 新增 /api/product-skus/**、/api/categories/** 权限行）
8. `UPDATE sys_excel_template ...`（如模板定义引用了旧字段名）
- ID 全部保留原值（rename 天然保证），历史单据无感

### Step 4：Java 全域重命名（只改名，不改任何业务逻辑）
- 实体：`Product`→`ProductSku`、`ProductSpu`→`Product`（**先把 Product 改成 ProductSku，再把 ProductSpu 改成 Product**，避免中间态重名）
- Repository/Service/DTO/Controller、JPQL、原生 SQL、@JoinColumn 按审计清单逐项落实
- API 路径：`/api/product-skus`（SKU）、`/api/products`（SPU）、`/api/categories`
- 编译通过 → 提交
