## 2026-08-09 补充：归档方案与执行前门禁

### 本轮结论

- 本轮只完成了代码、接口契约和历史核对记录的复核，**没有**调用订单取消、作废、拣货、预留或库存写接口。
- 应用的 `/health/check` 返回 HTTP 200；实时 OpenAPI 中存在销售订单 `POST /api/sales-orders/{id}/void` 与 `POST /api/sales-orders/{id}/cancel` 端点。
- 历史核对表仍是本次处置的唯一业务基线；本机没有可用的 PostgreSQL 命令行客户端，且页面浏览器连接初始化失败，因此本轮未将该基线重新查询为实时数据库快照。真实处置前必须重新执行该只读核对。

### 为什么不能直接调用现有“作废”接口

现有 `voidSalesOrder` 对 `APPROVED_AWAITING_SHIPMENT` 订单会：

1. 拒绝存在已完成拣货任务的订单；
2. 释放仍处于打开状态的预留；
3. **物理删除**该订单的出库任务；
4. 将订单状态改为 `VOIDED` 并追加订单审计。

订单 13、14 的历史基线虽然显示预留和库存流水均为 0，但任务 1、2、3 是应保留的测试证据。直接调用现有作废接口会删除这些任务，违背“可审计作废/归档、不得直接删除历史任务”的暂定原则，因此不得用于本次处置。

### 推荐的后续实现：专用历史测试数据归档

后续应新建独立、受保护的归档能力，而不是复用通用取消/作废接口。最低约束如下：

- 仅允许精确指定的历史测试订单及其关联待拣任务作为同一事务单元处理：订单 13 + 任务 1、2；订单 14 + 任务 3。
- 执行前锁定订单、任务、预留和库存流水记录，再次断言：任务均未完成、预留总量为 0、没有关联库存流水，且订单/客户/商品/备注仍含历史测试标识。
- 订单保留原始编号和明细，标记为 `VOIDED`/归档；出库任务不得删除，应新增可审计的归档/作废状态或等价归档字段，并从正常待拣队列排除。
- 不得增加、扣减、释放或重算库存；不得新增库存流水；不得改变批次余额。
- 必须记录操作人、时间、原因、处置前后快照及关联对象 ID；任一前置断言失败时整个事务回滚。
- 执行接口必须限制为受保护管理员，要求二次确认及固定处置理由；不能作为通用订单清理入口。
